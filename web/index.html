01 · Problem

Problem

People use a workplace AI assistant across weeks of meetings while projects hand off, SQL warehouses migrate, and status report formats change.

4 Memory Baselines Tested on Bedrock

Keeping User Context Current Across Weeks of Meetings

14 Sessions · 2 Personas · 5 Contradictions

If an assistant starts every chat with a blank slate, you spend time re-explaining which project you own, which SQL dialect your warehouse uses, and how your team formats weekly updates. If it instead pastes six months of raw chat logs into the prompt, old assignments remain right next to current ones, and the model writes queries for a decommissioned Redshift cluster on a project you handed off weeks ago. QuickMemory stores facts in a directed graph per user: when an assignment or preference changes, the old link is marked superseded rather than sent to the model, and clicking Forget removes a node and its incident edges immediately.

01 · STATELESS SESSIONS

Fresh Chats Score 6.9% Context Recall

Without persistent state, every new chat loses the user's active project, SQL dialect, and report format, requiring repeated prompting and reaching 6.9% slot recall on live us.amazon.nova-lite-v1:0.

02 · FULL TRANSCRIPT STUFFING

100.0% Stale Fact Exposure & Linear Token Growth

Appending raw session logs grows linearly with session count (1,180 average input tokens across 7 sessions) and leaves superseded Q3 facts (Payments-v1, Redshift SQL) in the prompt on 100.0% of queries, scoring 0.0% contradiction-clean accuracy.

03 · FLAT VECTOR CHUNKS

75.0% Stale Contamination & Missing 2-Hop Context

Top-K cosine search retrieves old Session 01 chunks alongside newer ones (75.0% stale exposure, 25.0% contradiction accuracy) and misses second-hop metrics and blockers not named in the prompt (65.5% recall).

02 · Architecture

Architecture

Request and session consolidation pipeline across CloudFront, S3, Python 3.12 AWS Lambda, and Amazon Bedrock. Click any component below to inspect its module and measured metrics.

Serverless Python 3.12 + Amazon Bedrock
STEP 01 · CONSOLIDATION

Entity & Relation Extraction

Parses session notes into Person, Project, Metric, System, Preference, and Commitment nodes linked by directed edges (OWNS, PREFERS_FORMAT, BLOCKED_BY, COLLABORATES_WITH).

STEP 02 · CONTRADICTION CHECK

Slot Supersession Lineage

Detects functional slot updates (such as Payments-v1 → Checkout-Latency-Q4 and Redshift → Athena Iceberg SQL), marks prior edges SUPERSEDED, and links explicit SUPERSEDES provenance.

STEP 03 · 2-HOP RETRIEVAL

Sub-Millisecond Subgraph Packing

Scores active nodes with BM25, 3-gram cosine similarity, and Ebbinghaus retention exp(-λt / (1 + 0.48 ln(1+n))), walks 2-hop active edges in 0.624 ms p50 / 1.029 ms p99, and packs compact triples (-49.5% input tokens).

STEP 04 · GENERATION & PRIVACY

Cited Responses & Instant Forget

Calls live us.amazon.nova-lite-v1:0 with inline [MEM-xx] and [EDGE-xx] citations while supporting Pin (locks retention at 100%) and Forget tombstoning (6/6 = 100.0% prune verified).

03 · Implementation

Implementation

Python 3.12 graph engine (quick_memory/graph_engine.py) and serverless API router (quick_memory/server.py) handling entity extraction, contradiction supersession, retention decay, and two-hop retrieval.

10/10 Unit Tests Passing
MODULE 01 · CONSOLIDATION graph_engine.py :: ingest_live_transcript()

1. Entity & Relation Extraction

Instead of storing raw paragraphs verbatim, QuickMemory extracts discrete entities from meeting notes (projects, teammates, target metrics, blockers, and formatting rules) and links them with directed edges.
Splits multi-turn transcripts into speaker-stripped clauses and runs ordered structural extractors producing MemoryNode dataclasses across 6 entity classes (Person, Project, Metric, System, Preference, Commitment) and 7 directed MemoryEdge types (OWNS, PREFERS_FORMAT, BLOCKED_BY, TRACKS_METRIC, COLLABORATES_WITH, COMMITTED_TO, SUPERSEDES). Repeated mentions increment access_count += 2 and append session IDs to provenance_sessions.
MODULE 02 · SUPERSESSION graph_engine.py :: upsert_entity_with_relation()

2. Slot-Based Contradiction Supersession

When a user switches primary projects or migrates from Redshift to Athena Iceberg SQL, QuickMemory marks the previous edge superseded while keeping an audit record of which session replaced it.
Functional preference and ownership edges carry a canonical slot_key (primary_project, sql_dialect, code_stack, doc_format, active_blocker). On upsert, any active edge matching (source_id, relation, slot_key) or an explicit contradicts_label transitions atomically to status="SUPERSEDED", records superseded_in_session, and creates a SUPERSEDES lineage edge, keeping stale prompt exposure at 0.0%.
MODULE 03 · RETENTION graph_engine.py :: compute_ebbinghaus_retention()

3. Frequency-Reinforced Ebbinghaus Decay

A passing comment from five weeks ago decays faster than a formatting preference used every week. Users can also pin core preferences to lock their retention weight at 100%.
Computes continuous retention via R(t, n) = exp(-λ · age_days / (1 + 0.48 · ln(1 + access_count))) with default λ = 0.045. Every two-hop retrieval increments access_count on matched active nodes, flattening their decay curve over a 60-day window. Setting pinned=True clamps R = 1.0, and forgotten=True clamps R = 0.0.
MODULE 04 · RETRIEVAL & PRIVACY graph_engine.py + server.py

4. Two-Hop Subgraph Packer & O(deg(v)) Tombstoning

When a user asks to draft a weekly update without naming a project, a two-step walk from the user node finds the active project on hop 1 and pulls in its target SLA and active blocker on hop 2.
Combines BM25 IDF (k1=1.2, b=0.75) and character 3-gram cosine similarity weighted by 0.55 + 0.45·R(t,n) to pick hop-1 seeds, attaches active Preference nodes, expands hop-2 active edges in 0.624 ms p50 / 1.029 ms p99, and formats compact triples (596 mean Bedrock inputTokens). Calling DELETE /api/memory/forget sets TOMBSTONED and marks incident active edges PRUNED in O(deg(v)) time (6/6 = 100.0% verified).
04 · Trade-Offs

Trade-Offs

Comparing prompt token budget, multi-hop recall, write-path latency, and deletion behavior across the four evaluated memory architectures.

Measured Across 4 Baselines

1. Two-Hop Graph Triples vs. Flat Vector Chunks & Full Transcripts

  • Token Footprint vs. Second-Hop Recall: Flat top-3 cosine chunks send fewer input tokens (329 vs. 596 for QuickMemory), because they include only 3 short snippets. However, flat chunks miss second-hop blockers and metrics and pull in superseded Q3 turns, dropping recall to 65.5% and exposing stale facts on 75.0% of queries. QuickMemory spends ~267 extra tokens on structured two-hop triples to reach 89.7% recall (+24.2 pts) with 0.0% stale exposure, while using 49.5% fewer tokens than full transcript stuffing (1,180 tokens).
  • Scaling Over Long Histories: Full-history stuffing grows as O(S) with total sessions S. QuickMemory's prompt payload scales as O(|V_active_2hop|), bounded by the user's active projects and preferences whether S = 10 or S = 500.

2. Synchronous Clause Extraction vs. Async LLM Consolidation & Tombstones

  • Write-Path Latency vs. Open-Vocabulary Extraction: Calling an LLM on every session write adds 1.5 to 3.0 seconds of latency and extra token cost. QuickMemory runs deterministic clause and slot extraction on the synchronous write path (< 1 ms consolidation) for immediate updates, and can pair with background LLM entity linking for unstructured prose.
  • In-Place O(deg(v)) Tombstoning vs. Vector Re-Indexing: Removing a person or project from sliding-window text embeddings leaves partial mentions across overlapping chunks. Graph tombstoning (TOMBSTONED plus PRUNED incident edges) cuts retrieval paths atomically in O(deg(v)) without re-indexing transcripts.
